## 0. ROOT CAUSE SUMMARY

After the Phase 5 portal isolation work, three things broke:

1. **Delivery portal is isolated but data-starved** — the delivery staff can log in but sees no ready orders and no menu. This means the delivery portal's API calls are either hitting wrong endpoints, carrying wrong branch scoping, or the backend routes are rejecting the delivery staff JWT on data-fetch routes they should be allowed to read.

2. **Chef portal is isolated but order-starved** — a chef (e.g. Aberash) logs in and sees no incoming orders from the delivery staff portal. This means either the Socket.IO room wiring is wrong for role-scoped sessions, or the kitchen queue API endpoint is rejecting the chef JWT, or orders created by delivery staff are not being emitted to the correct kitchen Socket.IO room.

3. **Walk-in order channel still exists** — this restaurant is delivery-only. The `walk_in` channel and any related UI/logic must be fully removed from the entire codebase.

Additionally, the lottery engine needs a targeted change: lucky numbers should generate automatically when an order code is created, be visible in the admin panel, and the admin copies and sends them manually — no automated Twilio send for lucky numbers (keep Twilio only for winner notifications if configured).

Fix these in the exact order listed below.

## 1. FIX — DELIVERY PORTAL: MENU NOT LOADING

### What's broken
The delivery staff portal's menu picker (used in the Relay Order tab to select food items) is showing empty. The menu data exists in the database — it's showing correctly in the admin panel. The delivery portal is not fetching it correctly after the Phase 5 role-scoping changes.

### How to fix

**Step 1 — Audit the menu API endpoint:**
Find the Express route that serves menu items (e.g. `GET /api/menu/items` or `GET /api/menu`). Check its middleware stack. After Phase 5, it likely has `requireRole('super_admin', 'branch_manager')` or similar that excludes `delivery_staff`. 

**Fix:** The menu read endpoint must allow ALL authenticated roles to fetch menu data — chefs, delivery staff, order intake staff, and admins all need to read the menu. Change the middleware to `requireAuth` (any valid JWT) for read operations (GET), while keeping write operations (POST, PUT, DELETE — add/edit/delete menu items) restricted to `super_admin` and `branch_manager` only.

The correct pattern:
```
GET  /api/menu/items     → requireAuth (all roles can read)
GET  /api/menu/categories → requireAuth (all roles can read)
POST /api/menu/items     → requireRole('super_admin', 'branch_manager')
PUT  /api/menu/items/:id → requireRole('super_admin', 'branch_manager')
DELETE /api/menu/items/:id → requireRole('super_admin', 'branch_manager')
```

**Step 2 — Confirm branch scoping:**
The delivery staff JWT contains their `branch_id`. The menu fetch must return items for their branch (or items marked as available for all branches). Confirm the GET menu endpoint filters by `branch_id` from the JWT, not from a query param that the client could manipulate.

**Step 3 — Test:** Log in as a delivery staff member, open the Relay Order tab, confirm the menu categories and items load correctly. Items marked unavailable should show with a red "Unavailable" badge and be non-selectable.

## 2. FIX — DELIVERY PORTAL: READY ORDERS NOT APPEARING

### What's broken
Orders that a chef marks as "Ready" in the Chef Portal are not appearing in the logged-in delivery staff member's portal. They appear in the super admin's orders page but not in the delivery portal.

### Root cause (likely one of these — check all three)

**A) API route permission issue:**
The delivery queue endpoint (e.g. `GET /api/delivery/queue` or `GET /api/orders?status=ready`) has role middleware that excludes `delivery_staff` after Phase 5 changes.

**Fix:** The delivery queue endpoint must explicitly allow `delivery_staff` role:
```
GET /api/delivery/queue → requireRole('delivery_staff', 'super_admin', 'branch_manager')
```

**B) Branch scoping returning empty:**
The query filters ready orders by `branch_id` from the JWT. If the delivery staff member's `branch_id` is null or mismatched with the branch the orders belong to, zero results return. 

**Fix:** When creating a delivery staff account in the admin panel, `branch_id` MUST be assigned — it cannot be null. Add a validation check: if a `delivery_staff` user has `branch_id = null`, the staff management page should show a warning and the queue endpoint should return a clear error ("Your account has no branch assigned — contact admin") rather than silently returning empty.

**C) Socket.IO room mismatch:**
When a chef marks an order "Ready," a Socket.IO event fires. The delivery portal should be listening for this event and update the UI in real time. After Phase 5 changes, the Socket.IO room names may have changed or the delivery portal may be joining a different room than the one the chef's action emits to.

**Fix:** Standardize Socket.IO room naming across the entire codebase:
- All users join a room named `branch:[branch_id]` on connection (e.g. `branch:1`)
- Role-specific rooms: `branch:[branch_id]:kitchen`, `branch:[branch_id]:delivery`, `branch:[branch_id]:admin`
- When a chef marks an order ready, emit to BOTH `branch:[branch_id]` (all users in that branch) AND specifically `branch:[branch_id]:delivery` (delivery staff only)
- The delivery portal must join `branch:[branch_id]` and `branch:[branch_id]:delivery` on socket connect
- Never emit to a room by user_id or any dynamic per-user room — use branch + role rooms only

**Fix the Socket.IO connection in the delivery portal:**
```javascript
// On delivery portal socket connect:
socket.join(`branch:${user.branchId}`);
socket.join(`branch:${user.branchId}:delivery`);

// On chef marking ready — server emits:
io.to(`branch:${order.branchId}:delivery`).emit('order:ready', { order });
io.to(`branch:${order.branchId}:admin`).emit('order:ready', { order });
```

**Step — Test end-to-end:**
Open two browsers side by side — one logged in as a chef, one as a delivery staff member in the same branch. Have the chef mark an order ready. Confirm the delivery portal updates in real time without refresh. If it requires a refresh, the Socket.IO wiring is still wrong.

## 3. FIX — CHEF PORTAL: INCOMING ORDERS NOT APPEARING

### What's broken
When a delivery staff member submits a Relay Order from their portal, the order is created in the database but does not appear on the Chef Portal (Aberash's screen) in real time or even on refresh.

### Root cause (check all three)

**A) Kitchen queue API route excluding chef role:**
The KDS queue endpoint (e.g. `GET /api/orders/kitchen` or `GET /api/kitchen/queue`) has role middleware that excludes `chef` after Phase 5.

**Fix:**
```
GET /api/kitchen/queue → requireRole('chef', 'super_admin', 'branch_manager')
```

**B) Branch scoping issue — same as delivery (see Section 2B above):**
Chef's `branch_id` must not be null. Same validation applies.

**C) Socket.IO room mismatch for incoming orders:**
When the delivery portal submits a new order (POST /api/orders), the server must emit a Socket.IO event to the kitchen room for that branch. Check that this emit is actually happening in the order creation route handler.

**Fix:** In the POST /api/orders route handler, after successfully inserting the order:
```javascript
// After order is created:
io.to(`branch:${order.branchId}:kitchen`).emit('order:new', { order });
io.to(`branch:${order.branchId}:admin`).emit('order:new', { order });
```

The Chef Portal must be joined to `branch:[branch_id]:kitchen` on socket connect:
```javascript
// On chef portal socket connect:
socket.join(`branch:${user.branchId}`);
socket.join(`branch:${user.branchId}:kitchen`);
```

**D) Chef portal polling/fetching on load:**
Even before real-time arrives, the Chef Portal must fetch the current kitchen queue from the API on page load. If the API call is failing silently (wrong endpoint, wrong auth header), Aberash sees nothing even after a refresh. Check the browser network tab for the kitchen queue API call — confirm it returns 200 with data, not 403 or empty array.

**Test:** Submit an order from the delivery portal. Confirm it appears on the Chef Portal within 2 seconds without refresh. Also confirm it appears after a full page refresh (not just via socket).

**Frontend — Delivery Portal:**
- No walk-in references should exist here, but do a search and remove any found.

**Frontend — Chef Portal:**

**Frontend — Customer Webapp:**

## 5. LOTTERY ENGINE — MANUAL MODE UPGRADE

### Current behavior (what needs changing)
Currently the lottery system either sends lucky numbers via Twilio automatically or doesn't generate them at a well-defined trigger point. The client wants a simpler, more controllable flow for now.

### New required behavior

**Lucky number generation trigger:**
- Lucky numbers are generated at the moment an **Order Code is assigned** — i.e., when a new order is successfully created and gets its order code (`ORD-XXXX`). This happens for ALL delivery-channel orders (whatsapp_voice, whatsapp_relay, webapp).
- NOT when the chef accepts (that was the Phase 4 spec) — move the trigger earlier to order creation. The customer should have their lucky number from the moment their order enters the system.

**Lucky number storage:**
- Generate a unique 6-digit lucky number (100000–999999, unique per branch per day — same uniqueness logic as Phase 4 spec).
- Store it immediately in `lottery_entries` table: `order_id`, `branch_id`, `customer_phone`, `customer_name`, `lucky_number`, `draw_date` (today's date), `lucky_number_sent = false` (since we are NOT auto-sending via Twilio in this version).

**Admin panel display — Lucky Numbers view:**
- In the Admin Command Center → Lottery section, add a **"Today's Lucky Numbers"** live table showing all lottery entries for today:
  - Columns: Order Code | Customer Name | Customer Phone | Lucky Number | Time Generated | Copied? (toggle)
  - The **Lucky Number** column shows the full 6-digit number in a large, clear, copyable format — clicking it copies to clipboard with a toast "Copied #482917"
  - A **"Copied"** toggle checkbox per row so the admin can mark which ones they've manually sent to the customer via WhatsApp (this is a local UI state flag for the admin's convenience, stored in `lottery_entries.manually_sent` boolean column)
  - Real-time: new entries appear instantly (Socket.IO push) as new orders come in — no refresh needed
  - The table is sorted newest-first

**No automated Twilio send for lucky numbers:**
- Remove any cron job or trigger that auto-sends lucky numbers via Twilio/WhatsApp
- The admin sees the number in the panel and copies it manually to send via their own WhatsApp
- Add a clearly visible instruction banner at the top of the Lucky Numbers view: "Copy each lucky number and send it to the customer via WhatsApp manually. Numbers are generated automatically when orders are created."

**End-of-day Draw — keep as-is with one addition:**
- The draw mechanism already exists — keep it
- After the draw runs and winners are selected, display winners in a clear "Today's Winners" panel with: Winner Name, Phone Number, Lucky Number, Prize — in a format easy for the admin to screenshot or read from
- Add a **"Copy Winner Message"** button per winner that copies a pre-formatted WhatsApp message to clipboard:
  ```
  🎉 እንኳን ደስ አለዎ! / Congratulations!
  TG's Restaurant (ቲጂ ምግብ ቤት)
  Your lucky number #[XXXXXX] has WON!
  Prize: [prize description]
  Please contact us to claim your prize.
  ```
- The admin then pastes this into their WhatsApp and sends it manually — no Twilio required for winner notification either (unless Twilio is configured in Settings, in which case offer a "Send via WhatsApp" button as an option but not the default)
